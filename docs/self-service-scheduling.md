# Self-service scheduling — PR `issue/otr-3008`

**Status:** Draft · **Author:** imbenham · **Last updated:** 2026-08-03

> This doc covers the scheduling changes in PR `issue/otr-3008`, in two parts:
> **Part I** ejects the scheduling "shape" resources from Terraform (resource lifecycle);
> **Part II** reorganizes the admin surface around the real owners (admin UX). They are two
> halves of one change — the admin UX (II) only works because the resources became
> runtime-managed (I).
>
> The changes live on `issue/otr-3008` and are
> **tentative design**, open to revision in review. "Current state" sections describe
> **develop**: the baseline this PR changes. The forward-looking provider-owned
> credentialing / virtual-scheduling direction is a separate conversation, in
> [`virtual-scheduling-northstar.md`](./virtual-scheduling-northstar.md).

## Overview

Scheduling "shape" resources — Locations, their Schedules, and the default group-scheduling
graph (HealthcareServices + PractitionerRoles) — used to be provisioned and owned by
Terraform, which made every create/edit/deactivate a deploy and left runtime edits fighting
TF state. This PR moves them out of Terraform so their lifecycle lives in FHIR + the admin
UI (**Part I**), and reorganizes the admin surface around the real owner of a schedule — a
Location or a provider, with the PractitionerRole as the bridge (**Part II**). A fresh
environment boots **tabula rasa**; an instance ships whatever starter set it wants (possibly
nothing) as concierge pre-configuration, applied to all its environments.

# Part I — Eject scheduling resources from Terraform

## Problem

Terraform-managed FHIR resources have four structural problems for anything an
admin should own:

- **Every change is a deploy.** Adding a Location, fixing a support phone, or
  deactivating a schedule required an IaC change + apply — not an admin action.
- **State fights runtime.** Any runtime edit is drift TF wants to "correct" on the
  next apply, so admin edits were never durable.
- **State is a single shared global.** Because these resources lived in state,
  branch/config divergence could destroy or duplicate them (see
  [Transitional risk](#transitional-risk-shared-state-divergence)).
- **Setting a customer's location config required coordination** between the customer,
  product team, and dev teams.

The goal is to make these resources **runtime-managed and self-service** — created,
edited, and deactivated through the EHR admin UI — and to stop treating any of them as
"canonical": a fresh environment comes up empty, and each practice owns its own set.

## Current state (develop — the baseline this PR changes)

On develop today, the scheduling "shape" resources — Locations, their Schedules, the
default group-scheduling graph (HealthcareServices + PractitionerRoles), and the example
Practitioners/PractitionerRoles — are provisioned and **managed by Terraform** as
`oystehr_fhir_resource`s (generated by `deploy/generate-oystehr-resources.ts` from static
config; no runtime-seed removals). They're reconciled on every `terraform apply`: editing
one means an IaC change + deploy, and a runtime edit of any managed property is reverted by
the next apply. There
is **no runtime seeder** and **no dedicated self-service Location lifecycle** — the
`packages/zambdas/src/ehr/locations/` CRUD suite doesn't exist on develop. That is the
state this PR changes.

## What this PR introduces

The PR moves those resources out of Terraform state and stands up the runtime lifecycle.

**Ejection from state.** `deploy/oystehr/removed-locations.tf.json` carries a
`removed {}` block for each seed resource with `lifecycle { destroy = false }` — TF
drops the resource from state but leaves it in FHIR. The block set is **generated**
from `config/runtime-seed/` (`deploy/generate-oystehr-resources.ts` →
`generateRuntimeSeedRemovals`), so removals and seed data stay in sync from one
source of truth. That this ejection never accidentally *destroys* a resource is backed by
tests and a CI gate — see [Safeguards](#safeguards-for-the-ejection-guarantee).

**One-time bootstrap.** `deploy/oystehr/main.tf` declares a single
`terraform_data.seed_runtime_resources` node (`triggers_replace` is a constant, so it
runs once per environment on create) that shells out to
`npm run seed-runtime-resources`. TF tracks only this node — never the individual
resources — so admin edits are never reverted. It `depends_on = [module.seed]` to
order after the bootstrap gate. It fires on every fresh environment and seeds whatever the
instance ships in `config/runtime-seed/` — empty ⇒ nothing seeded (see
[Starter seed](#starter-seed-concierge-pre-configuration)).

**The seeder** (`packages/zambdas/src/scripts/seed-runtime-resources.ts`):

- Reads whatever the active instance ships under `config/runtime-seed/*.json`; the
  per-instance data lives there, so it's one script for all instances.
- POSTs each file's resources in a single FHIR transaction, resolving intra-file
  `#{ref/fhirResources/KEY/id}` placeholders to `urn:uuid` fullUrls.
- Strips Terraform-only placeholders (`#{var/...}`, cross-file refs) **along with the
  field that carries them** — these are optional integration fields (Stripe,
  AdvaPACS, lab identifiers) an admin now configures self-service, never
  booking-gating fields — so the result is always valid FHIR.
- **Idempotency is slug-anchored:** a file counts as already-seeded if any of its
  slug-bearing anchor resources (`identifier` with `SLUG_SYSTEM`) already exists.
  Re-runs and migrations of already-populated environments are no-ops. Incremental
  additions happen self-service, not by re-seeding.

Today's seed set: `config/runtime-seed/locations-and-schedules.json` (the default
Locations + Schedules) and `config/runtime-seed/visit-followup-group.json` (the
default group-scheduling graph).

## Design

### The lifecycle contract

After bootstrap, these resources are **FHIR-owned**. Terraform's only relationship
to them is the one-shot seeder node. The admin UI is the single writer for
create/edit/deactivate. This is the contract Part II builds on.

### Seed format & placeholder resolution

Each `config/runtime-seed/*.json` file is a `fhirResources` map of `KEY → { resource,
managedFields }`. Placeholders express references that only exist at seed/deploy time:

- `#{ref/fhirResources/KEY/id}` / `.../type` — intra-file references, resolved to a
  transaction `urn:uuid` (or literal resourceType).
- `#{var/...}` and cross-file refs — Terraform-only; stripped with their carrier.

`managedFields` annotates the seed data (e.g. `["identifier"]`) and feeds the
removal-block generator; the seeder itself doesn't consume it. With seeding reframed
as a one-shot starter (below), there's no overlay/base-merge for it to drive — it
stays purely an input to removal-block generation.

### Safeguards for the ejection guarantee

Ejecting a resource is only safe if it stays represented (a `destroy:false` removal, so
`apply` drops it from state rather than destroying it) and reproducible (a seed entry).
Three layers protect that — the risk being that a resource silently leaves Terraform
config with no removal block, which `apply` would **destroy**, not eject.

1. **By construction + unit test.** `generateRuntimeSeedRemovals` derives exactly one
   `removed { destroy = false }` block per seed resource key, so the removal⇄seed sync and
   the non-destructive flag are structural, not hand-maintained. A unit test locks these
   invariants (one block per key, `destroy = false`, and an empty seed set → the removals
   file is deleted, leaving no stale blocks).
2. **Cross-branch completeness (CI).** The by-construction sync guarantees removals match
   the seed — but *not* that the seed captured everything the target branch still manages.
   A CI check (`deploy/check-ejection-coverage.ts`, itself unit-tested) diffs the generated
   managed-resource set against the PR's target branch and **fails the PR** if any
   `oystehr_fhir_resource` leaves Terraform management without a `destroy:false` removal
   backed by seed data — i.e. would be destroyed on apply rather than ejected. (Edge cases,
   the algorithm, and CI wiring are documented inline in `deploy/check-ejection-coverage.ts`,
   `.github/workflows/ejection-coverage.yml`, and the check's unit tests.)
3. **Merge-time discipline (drift).** The CI check reflects the target branch as of its
   run; if the PR sits while the target advances, that baseline goes stale. Close the
   window by making the check a required status check with "require branches up to date
   before merging" — or, absent that setting, by syncing the target branch and confirming
   the check re-runs green immediately before merge (ideally in a low-activity window).

### Soft-delete by default; guarded hard-delete as the escape hatch

Deactivation is the routine control: status-based (`Location.status`, `Schedule.active`,
`HealthcareService.active`, PR `active`), never a FHIR delete — a plain delete would
orphan the Schedules/PractitionerRoles that point at a Location and break the slug
lookup booking depends on. The admin lists filter inactive resources out of the default
view, so "archived" just means inactive; **nothing ever auto-deletes long-inactive
resources** (they're cheap and carry history — removal is only ever the explicit
hard-delete below).

For the narrow "created in error" case there is a **guarded hard-delete** (Location only
so far — the `delete-location` zambda, Admin / Customer-Support only):

- Two-phase: a first call refuses with `RESOURCE_HAS_DEPENDENTS` when the Location has
  dependent Schedules/PRs or any Appointments, so the UI shows a destructive-action
  warning; a `force` retry proceeds.
- On force it cascade-deletes the dependent Schedules + PRs (which would otherwise
  dangle) and the Location. Appointments are never deleted (clinical history is kept) —
  their location reference is simply orphaned, which Oystehr permits (verified by the
  integration test; the dedupe tool's "never delete an anchor with Appointments" is a
  deliberate safety choice, not a server constraint).
- Because it removes the resource entirely, it also **frees the slug** for reuse —
  something deactivation can't do.

### Starter seed: concierge pre-configuration

There are no "canonical" scheduling resources — each practice's Locations are its own, and
nothing from Ottehr-core belongs in every environment. `config/runtime-seed/*.json` serves
two purposes:

- **Concierge pre-configuration.** It's where an Ottehr team hands a new instance a working
  starter set — that practice's real Locations/Schedules — as a service. A per-instance
  convenience starting point, not a source of truth: once seeded it's fully runtime-owned and
  freely editable, exactly like anything an admin creates by hand.
- **Anti-deletion safety.** It's the source the `removed{}` blocks are generated from, so
  unplugging those resources from Terraform leaves them intact in FHIR (see
  [Safeguards](#safeguards-for-the-ejection-guarantee)).

A fresh environment boots **tabula rasa** simply by shipping an empty `config/runtime-seed/`
(the seeder no-ops). An instance opts *into* pre-configuration by putting its starter
resources there; whatever it ships is seeded to **all** its environments — there is **no
per-environment gating flag**, since an instance that wants its locations wants them
everywhere.

Because it's a one-shot starter rather than an ongoing canonical source, there is **no
overlay/base-merge mechanism** — which is also why `merge=ours` on `config/runtime-seed/` is
fine: an instance's starter content is read once and then owned outright, so drift from
upstream is irrelevant.

**Test fixtures under tabula rasa.** The seed exists for pre-configuration, **not** to
provision test data — so the e2e harness can't assume it's populated. Today the harness
(`scripts/e2e-test-setup.ts`) looks up its in-person Location from whatever the instance's
`config/runtime-seed/` defines (deployed by the seeder), and when the seed defines **none**
(a genuinely empty instance) it **synthesizes a minimal in-person Location**
(`ensureSyntheticE2eLocation`) so the suites still run. So a new instance is e2e-runnable out
of the box, while an instance can still exercise its own specific-shape fixtures via its
seed. Two consequences, both by design:

- **Telemed e2e self-skips** on a tabula-rasa instance — no virtual Location ⇒
  `isTelemedEnabled` is false ⇒ the telemed specs `test.skip`. An instance that wants telemed
  exercised defines a virtual Location in its seed (which re-enables them). A skipped telemed
  suite on an empty instance is expected, not a regression.
- **Group-scheduling specs self-provision** their own HealthcareService + Location +
  Practitioner fixtures at runtime, independent of the seed — so no group fixture is
  synthesized, and none is needed (there are no production users of group scheduling).

Integration tests are already self-contained (`setupIntegrationTest` creates its own Location
+ appointment graph per test), so they run against an empty instance unchanged.

> **Future work (later PR): fully decouple e2e from the seed.** The synthetic-Location
> fallback is a bridge, not the destination. The durable goal is for **EHR e2e to provision
> and tear down its own resources the way the intake suite already does** — so the e2e suites
> depend on no seed data at all and the fallback can be removed. This is the explicit
> end-state of separating the seed's concierge/anti-deletion mission from test provisioning.

### Versioning

Canonical FHIR resources are referenced by URL + version and bumped via
`npm run bump-canonical-version` (never edited in place); the runtime-seed files
carry `schema-version` (currently `2025-09-25`).

Because the seed is a one-shot starter that's owned outright after bootstrap,
propagating later `config/runtime-seed/` revisions to already-seeded environments is a
non-goal — post-bootstrap changes are self-service admin actions. (Canonical _global_
resources seeded by `module.seed` — global templates, EM codes, etc. — still version
via `bump-canonical-version`; that's a separate concern from the scheduling starter.)

## Migration & rollout

### Phases

- **Phase 1 — this PR.** Mechanism (removed-blocks + generated sync + one-shot seeder),
  default set migrated, slug-anchored idempotency, soft-delete toggles for the core
  resources.
- **Phase 2 — self-service field coverage.** Every field an admin should own is
  editable in the UI (support phone landed here); no residual TF-only fields that
  gate scheduling.
- **Phase 3 — retire the migration scaffolding.** Once every environment is past the
  migration, remove the removal-blocks mechanism, the ejection-coverage safeguards, and the
  transitional tooling — see [Cleanup](#cleanup-what-can-be-removed-and-when).

### Transitional risk: shared-state divergence

While the migration is **in flight against a shared environment**, the ejection is a
one-way state change that other configs don't yet know about. An apply from a config
that _still declares_ these resources (e.g. `develop`, or an unmerged branch) finds
them "in config, not in state" and re-creates them. The Oystehr provider's create is
a **plain unconditional POST — no conditional-create/upsert** — so this produces
**duplicates that share a slug**, and since booking resolves owners by slug, the
collision causes ambiguous lookups.

Two mitigations, both transitional:

- **Prevention — state snapshot/restore.** `deploy/state-snapshot.sh` /
  `state-restore.sh` capture a workspace's state before deploying an ejecting branch
  and restore it after, so a later divergent apply still sees the resources in state
  and doesn't re-create them. (See `deploy/TERRAFORM-STATE-SNAPSHOT.md`.)
- **Cleanup — dedupe.** `dedupe-scheduling-resources.ts` finds slug-collision
  duplicates among the anchor types (Location, HealthcareService, Practitioner),
  keeps the oldest, deletes the newer copies + their orphaned Schedules/PRs, and
  never deletes an anchor that has real Appointments. Dry-run by default; `--apply`
  to act.

Both are obsolete once all environments are migrated (Phase 3).

#### Looking ahead: conditional-create de-risks the *next* migration (not this one)

The root cause is that the provider's create is an unconditional POST. FHIR conditional
create (`If-None-Exist`) **is** supported at the Oystehr FHIR layer (both
`fhir.create({ ifNoneExist })` and `BatchInputPostRequest.ifNoneExist`); it's simply not
exposed by the `oystehr_fhir_resource` Terraform resource, whose only attributes are
`data` / `type` / `managed_fields` / `removal_policy` (and a computed `id` that can't be
pinned). If the provider issued a conditional create keyed on the slug identifier, a
re-create would **adopt the existing resource by slug instead of duplicating it**, and —
paired with `managed_fields: ["identifier"]` — wouldn't revert runtime edits.

Important caveat, though: this **cannot fix the current migration**. The behavior would
live in the Terraform inputs — either a per-block `if_none_exist` attribute or the pinned
provider version — and a stale branch that already exists has neither, so its apply still
POSTs unconditionally and duplicates. (Only a purely server-side change — treating any
identifier-bearing POST as conditional — would help retroactively, which is a far bigger,
non-standard ask.) So conditional-create is a **forward-looking improvement for future
eject-from-state migrations**: adopt it *before* creating the branches that will diverge
and the duplication class never arises. Worth prioritizing the upstream provider feature
for that reason — it does not, however, retire the transitional tooling here.

### Cleanup: what can be removed, and when

Much of this PR is **one-time migration scaffolding**. It becomes inert — and should be
deleted — once **every environment across every project/instance has applied the deploy
that ejects these resources** (so no environment's Terraform state still manages them and
the runtime seed has taken over). That is the gate, and the ordering matters for safety.

> ⚠️ **Do not remove the removal blocks before that gate.** On an environment that hasn't
> applied yet, the resources are absent from config but still in state; without the
> `removed{}` block, its next `apply` would **destroy** them. So the removals — and the CI
> check guarding them — must outlive the slowest environment. Confirming "everyone has
> applied" requires a tracked rollout across instances; treat that audit as the
> prerequisite for pulling any of this.

**Removable once fully rolled out** (this is Phase 3):

- The **removal-blocks mechanism** — `generateRuntimeSeedRemovals` in
  `deploy/generate-oystehr-resources.ts` and the generated
  `deploy/oystehr/removed-locations.tf.json`. They become no-ops: a fresh env never had
  these in state, and every existing env has already dropped them.
- The **safeguards that exist only to guard that mechanism** —
  `deploy/check-ejection-coverage.ts` + its unit test, the
  `.github/workflows/ejection-coverage.yml` workflow, and the `generateRuntimeSeedRemovals`
  unit test. (No future ejections are planned — new resources are created self-service, not
  moved out of TF — so once the mechanism is gone these guard nothing.)
- The **shared-state transitional tooling** — `deploy/state-snapshot.sh`,
  `deploy/state-restore.sh`, `deploy/TERRAFORM-STATE-SNAPSHOT.md`, and
  `packages/zambdas/src/scripts/dedupe-scheduling-resources.ts` (whose header already flags
  itself obsolete at this point).

**Must stay** — not scaffolding, but the durable self-service mechanism:

- The **seeder** (`seed-runtime-resources.ts`) + `config/runtime-seed/` + the
  `seed_runtime_resources` bootstrap node — the ongoing concierge starter seed,
  independent of the removal blocks.
- The **self-service Location lifecycle** — the `packages/zambdas/src/ehr/locations/` CRUD
  zambdas and the admin UI (Part II).

## Risks & tradeoffs (Part I)

- **No upsert in the provider** is the root of the duplication hazard; the whole
  transitional apparatus exists to work around it. The FHIR layer does support
  conditional create, but the provider doesn't expose it — see
  [Looking ahead](#looking-ahead-conditional-create-de-risks-the-next-migration-not-this-one).
- **Slug as the identity key** — idempotency, dedupe, and booking all key on the
  slug. It's load-bearing; anything that mints a resource in this set must set a
  correct, unique slug.
- **One-shot seeding** means seed-data changes never reach existing envs
  automatically (a non-goal — see [Versioning](#versioning)) — intentional, but a
  footgun if someone expects edits to `config/runtime-seed/` to propagate.

## Resolved decisions (Part I)

The design questions are settled; what remains is execution (the Phases).

- **Seeding model** — no "canonical" resources and no overlay mechanism; the seed is a
  one-shot **concierge** starter (per-instance, no per-env flag), owned outright after
  bootstrap (`merge=ours` is therefore fine). `managedFields` is just input to removal-block
  generation.
- **Seed-data revision propagation** — a non-goal; post-bootstrap changes are
  self-service.
- **Deletion** — soft-delete (deactivate) by default; a guarded hard-delete escape
  hatch (this PR, for Location) for the created-in-error case; nothing auto-deletes
  long-inactive resources.
- **Provider conditional-create** — the FHIR layer supports it, the provider doesn't
  expose it; it's a forward-looking de-risking improvement for *future* migrations of
  this shape, **not** a fix for the current transitional tooling (a stale branch's
  inputs wouldn't carry it). See
  [Looking ahead](#looking-ahead-conditional-create-de-risks-the-next-migration-not-this-one).

# Part II — Scheduling admin refactor

## Problem (the develop admin surface)

- **The admin surface was Location-shaped.** Schedule management was split across
  Location- and Provider-owned tabs, with owner configuration entangled into the schedule
  page. Providers-with-schedules and Locations-with-schedules are different enough that a
  single Location-centric framing served neither well.
- **Direct-to-FHIR writes** for status toggles and creates scattered business rules into
  the client and made permission boundaries fuzzy.
- **Capability and jurisdiction live on the wrong resource** ("this provider does telemed
  in NJ" is modeled as "there's a virtual Location whose state is NJ"). That thread is
  the northstar and lives in [`virtual-scheduling-northstar.md`](./virtual-scheduling-northstar.md);
  this part covers only the admin-surface reorganization.

## What this PR introduces

Reorganizes the admin surface around a simple idea: **a schedule is owned by either a
Location or a provider, and a PractitionerRole is just the bridge that binds a provider to
a location so it can own a schedule.**

**Combined Schedules list.** Location- and Provider-owned schedules render in one
expandable, filterable table (`SchedulesTable`): each provider row expands into its
"provider · location" schedule children; filters for search / owner-type / active; the
Address and Support-phone columns were dropped. Schedule-less Locations are filtered out
(they're created via "Add schedule"). Status is shown via a shared `BooleanStateChip`
(green active / grey inactive) standardized across resource lists.

**Unified create flow.** A single create-schedule page handles both paths — Provider
(→ `createPractitionerRole`, minting the bridge PR + a blank Schedule) and existing
Location (→ `createSchedule`) — with an owner-type step and `?provider=` pre-fill (which
resolves either a User id or a Practitioner id).

**Provider-centric model.** The PractitionerRole is treated purely as the bridge between a
Provider+Location pair and a schedule; Locations, by contrast, have lives beyond
schedule-owning. Consequences:
- The schedule page acts on the **Schedule resource alone** (timezone / slug / booking
  links + a `Schedule.active` toggle). PR name/active editing moved to
  `PractitionerRoleList`; location/services are create-time-only.
- Provider rows are keyed by **Practitioner id**; the owning User id is resolved lazily
  only when needed, via a dedicated `/admin/provider/:practitionerId` route (so the list
  doesn't scan every project user).

**Provider groups** promoted to a first-class "Provider groups" nav item (in a "Practice"
section with Locations / Services / Schedules): a landing page (Name / Pool / Services /
Active), a create page, and a detail page. Groups restrict which services their pooled
providers offer.

**Writes behind zambdas.** A per-resource active-toggle pattern
(`toggle-location-active`, `toggle-schedule-active`, `toggle-group-active`,
`admin-set-practitioner-role-active`) plus create/update/delete zambdas replace
direct-to-FHIR writes, each with its own permission boundary. Support-phone editing moved
onto the Location config page as a first-class field.

**Performance.** `list-schedule-owners` was reworked to scope its fetches (owner-side
`_revinclude` for Location/Group schedules; PR-bundle-only for providers; lazy user
resolution), cutting the Schedules list load from ~10s to ~1.5s.

## Non-goals (Part II)

- The resource **lifecycle** (seeding, delete, runtime-management) — that's Part I.
- The **service-mode / jurisdiction** data-model change — the northstar
  ([`virtual-scheduling-northstar.md`](./virtual-scheduling-northstar.md)).
- Employees-vs-Providers nav consolidation (explicitly deferred).
